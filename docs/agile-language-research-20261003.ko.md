### 추가로 확인한 문맥 관리와 조립법

[Meta의 9월 2일 개발 기록](https://engineering.fb.com/2026/09/02/ml-applications/organizational-second-brain-ai-learns-from-experts/)은
지식 파일과 절차를 분리하고, 각 단계에 필요한 자료를 불러오는 조립식 절차를 설명한다.
Gooo에는 타입·허용 연산·기대값을 데이터로 두고, 조건부 보정·범위 제한·두 연산의 순서를
매개변수 조립법으로 재사용하는 원리를 가져온다. 이 시스템은 사람의 피드백과 검토를 사용한다.
Gooo에서 자동 수집할 개선 근거는 선언된 기준 함수와 실행 결과다.

긱뉴스에서 찾은 [Context Language Models](https://arxiv.org/abs/2609.37725v1)는
9월 29일 공개됐고, 모델이 다음 호출의 문맥을 파일처럼 편집하는 방식을 연구한다.
Gooo에 적용할 작은 질문은 **다음 선택에 필요한 실행 사실을 얼마나 작게 유지할 수 있는가**다.
원본 의도와 관측 이력은 보존하고, 현재 남은 후보·구별되는 입력·실패 원인을 제한된 작업
배열에 정리하는 방식을 우선한다. 논문의 접미 캐시 재사용은 이전 문맥에서 계산한 상태를
쓰는 근사법이므로, Gooo의 정확한 후보 출력 재사용과 비용을 따로 비교해야 한다.

두 자료가 제시한 실행 환경을 통째로 붙이는 대신, 다음 작은 기능의 판단 기준으로 쓴다.
세 조립법으로 같은 입력·대안·실행 결과를 더 짧게 표현할 수 있는지 먼저 관측한다.
학습 업데이트 0회인 경로와 기존 자체 모델을 연결한 경로를 함께 유지한다.
조립법 선택, 내부 경로 선택, 최종 실행 충족률을 각각 기록하면 어디에 학습이 필요한지 보인다.

## 학습 규모를 어떻게 줄일 것인가

[Meta LLM Compiler](https://arxiv.org/abs/2407.02524)는 2024년의 관련 선행 연구다.
7B/13B 모델, 546B 토큰의 컴파일러 중심 학습과 추가 과제 학습을 사용했다.
Gooo에서는 IR의 가능한 행동을 좁히는 원리를 참고하고, 다음과 같은 작은 단위로 개발한다.

1. **타입·변수 범위·데이터 의존성은 컴파일러가 계산한다.** 이미 정확하게 알 수 있는 사실에
   모델 학습량을 쓰지 않는다.
2. **모델은 짧은 한영 의도와 합법적인 대안의 순위를 연결한다.** 예를 들어 경계값 포함 여부,
   두 피연산자의 순서, 먼저 갱신할 변수처럼 손에 잡히는 선택이다.
3. **테스트에서 얻은 사실은 다음 시도에 바로 사용한다.** 실패 하나를 배울 때마다 GPU 학습을
   다시 돌릴 필요는 없다. 가중치 갱신과 실행 중 기록 사용의 비용을 각각 센다.
4. **자주 성공한 조립법은 명시적인 매개변수 조립법으로 남긴다.** 처음에는 `clamp`, 조건부 보정,
   누적 같은 몇 가지 프로그램으로 시작하고 소스 ID·타입·입출력 계약을 함께 재사용한다.

언어의 사용성을 판단하는 첫 기준은 특정 업무에서 선언한 기능을 끝낼 수 있는가다.
한 번에 맞힐 비율은 탐색 비용을 설명하는 보조 지표로 둔다. 새 도메인·장문·모든 표현에 대한
일반화는 별도 실험에서 범위를 넓혀 확인한다.

## 이번에 구현한 첫 기능: 다음 관측 입력 선택

Go SDK의 `PreparedPlan.RankProbes`가 고정된 선언 후보와 기존 테스트를 받는다.
기존 테스트를 만족하는 후보들에 대해, 주어진 관측 입력에서 어떤 값이 나오는지 계산한다.
다른 출력을 만드는 후보 쌍이 가장 많은 입력을 다음 관측으로 제안한다.
동점이면 가장 큰 동일 출력 집단이 작은 입력, 그다음 선언 순서를 사용한다.

예를 들어 `x - 2`와 `2 - x`는 `x=2`에서 모두 0이다. 다음 입력을 3으로 잡으면
각각 1과 -1이 된다. 별도로 선언된 기준 구현이 3의 기대값을 -1로 돌려주면 후보가 하나 남는다.
이때 시스템이 얻은 것은 새 실행 사실이며, 모델의 확신과 다른 종류의 정보다.

```text
Gooo의 허용 후보
  → 기존 예시를 만족하는 후보 유지
  → 후보 차이가 잘 드러나는 입력 선택
  → 기존 오라클 실행 / 관측 부족 기록
  → 기대값과 출처를 새 예시에 추가
  → 후보 조립을 이어가기
```

이 기능의 범위는 순수 정수 바디, 최대 후보 64개·기존 예시 128개·관측 입력 32개다.
후보 출력 행렬은 연속 배열 16 KiB다. 생성된 프로그램과 결과 문서 메모리는 별도로 사용한다.
모델 호출과 학습 업데이트는 0회다. 후보 예산이 전체 공간보다 작으면 `PARTIAL`로 표시하며,
동일 출력 후보가 남으면 모호함을 그대로 남긴다. 취소·마감시간과 결과 소유권을 검사한다.
기존 오라클이 없는 작업은 기대값 미확인 상태를 기록하도록 연결해야 한다.

이는 LAVOIR에서 얻은 “다음 정보의 쓸모”라는 질문을 Gooo의 작은 후보 공간에 적용한 구현이다.
점수는 구분되는 후보 쌍의 수이며, 학습된 정보 가치나 정답 확률로 부르지 않는다.
소스는 [Go SDK](https://github.com/kimjooyoon/gooo-decision-runtime/tree/main/examples/probe-ranking)에 공개한다.
SDK API·실행 예제에 이어 컴파일러 CLI의 `--path-observation`에도 연결했다.
같은 소스에 선언한 순수 기준 함수가 기대값을 공급하고, 실행 전에 원본 관측을 다시 확인한다.

실행 예제에서 남은 후보는 2개에서 1개로 줄었다. 이어서 실제 main 컴파일러가 Gooo를 Go로
생성했고, 다섯 입력의 네이티브 실행 검사가 모두 통과했다.
[원본 판단·생성·실행 기록](../publication/agile-probes-20261003/README.md)에 작은 예제의
범위와 처음 발견한 예제 오류, 수정 소스를 함께 기록했다.

## 다음 세 가지 언어 작업

| 순서 | 작은 범위의 작업 | 얻으려는 효과 | 측정 |
| --- | --- | --- | --- |
| 1 | 관측 입력 제안과 기존 테스트 오라클 연결 | 같은 예시에서 구별되지 않던 경로를 시스템이 좁힘 | 남은 후보 수, 관측 횟수, 오라클 비용, 관측 미해결 수 |
| 2 | 연산 순서를 보존하는 작은 특징 | “더한 뒤 곱하기”와 역순을 구별 | 순서 반례의 분리 수, 한영 양쪽 충족 수, 추가 조립 수 |
| 3 | 자주 쓰는 조립법 3개를 Gooo 선언에서 재사용 | 긴 계획 문서 없이 조건·대입·순서를 표현 | 선언 크기, 재사용 시 실패 수, 생성·실행 비용 |

두 번째 작업은 현재 모델의 전체 조각 빈도 표현이 연산 순서 반례를 같은 배열로 만드는 문제에
직접 대응한다. 구조 의존 간선과 인접한 연산 순서 특징을 먼저 대조한다. 필요하면 32–256개
작은 대비 과제로 짧게 학습하고, 개선 여부를 범위별로 공개한다. 이는 후속 계획이며 학습 성과는 아직 없다.

세 번째 작업의 차별화 지점은 **의도·합법 조립법·부족한 관측·다음 실행**을 같은 언어의
변경 가능한 기록으로 연결하는 것이다. 프로그램 합성·능동 관측·실패 기억 자체에는 풍부한
선행 연구가 있다. Gooo의 기여는 이 연결을 작은 실행 비용과 이해할 수 있는 표현으로 만드는 데 둔다.

## 관측에서 바로 코드로 이어가기: 구현과 측정

첫 번째 작업은 관측 루프, 출력 재사용, 유일 후보 직접 투영의 세 단계로 구현했다.
`reuse_probe_outputs`는 이미 계산한 후보 출력을 보관하고,
`resolve_unique_candidate`는 전체 후보를 확인해 하나가 남았을 때 그 몸체를 바로 구성한다.
남은 후보가 여럿이거나 예산이 부족하면 기존 탐색을 이어간다. 조립과 실행 결과의 연결은 계속 확인한다.

[직접 투영 실험](../publication/path-observation-resolution-20261003)은 120회 생성과
240회 실행, 대조군의 실제 소형 모델 판단 120회를 기록했다. 직접 투영한 24개 요청은
144/144 실행 기대값을 충족했고, 모델 호출과 추가 탐색은 0회였다. 모든 대조군까지 포함한
충족 수는 540/720이다. 한 과제의 한영 지시를 여섯 번 반복한 유한 관측이다.

모델 사용을 요청한 조건에서 재사용 후 탐색과 직접 투영의 생성 시간 중앙값은
9.491ms와 8.267ms, 최대 RSS 중앙값은 18.77MiB와 17.29MiB였다.
프로세스 CPU는 한 코어 기준 92.45%와 88.01%였다. 새 프로세스를 사용하는 조건이므로
모델 로딩 생략도 포함한다. 이미 모델을 보유한 작업자의 비용은 따로 측정해야 한다.

여기서 가져갈 원리는 **이미 관측으로 결정된 일을 다음 판단 단계까지 넘기지 않는 것**이다.
추가 학습 없이 작은 계약을 끝낼 수 있게 만드는 언어 기능이다. 새 기능의
소스·검사는 [#1164](https://github.com/kimjooyoon/meta-ontology-go/pull/1164)에 연결했다.

## 연산 순서의 작은 입력 특징

[128바이트 순서 특징 사전 실험](../publication/intent-order-preflight-20261003)에서
네 가지 연산 조합의 한영 지시·네 표현을 비교했다. 32쌍에서 기존 V4 특징이
정확히 같았고, 실제 자체 모델 64회 호출에서도 각 쌍의 판단이 같았다.
새 64칸 절 연결 배열은 이 32쌍을 구별했다. 추가 학습과 새 특징의 모델 호출은 0회다.

짧은 한영 문장을 처리하는 특징 생성은 M4에서 372–619ns/op, 힙 할당 0회였다.
이는 전체 코드 생성 비용과 별도 구간이다. `A B A C A D`와 `A C A B A D`처럼
절의 연결 횟수까지 같은 반복 순서는 여전히 구별되지 않는다. 그 반례도 함께 공개했다.

이 결과는 작은 학습 비교를 해볼 근거다. 새로운 정답률은 아직 없다.
기존 특징을 보존하고 순서 배열을 덧붙인 별도 입력 계약에서, 실제 조립된 바디의
충족률과 추가 시도를 확인할 계획이다. 매개변수 조립법은 별도의 다음 언어 작업이다.
