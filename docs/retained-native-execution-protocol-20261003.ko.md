# 다음 실험: 같은 조립물의 실행파일 한 개 보관하기

2026-10-03. 이 문서는 다음 실험의 계획입니다. 구현과 완료된 결과는 현재 없습니다.

## 관측에서 출발하기

[즉시 실행 예제](../publication/order-example-immediate-20261003)는 반복 생성 응답이
약 2ms인 동안, 컴파일과 두 번 실행하는 명령에 약 0.31~0.66초를 썼습니다.
네 결과의 실행파일 지문은 같았습니다. 빌드 97~267ms, 첫 실행 168~351ms,
두 번째 실행 4~8ms를 각각 기록했습니다. 첫 실행 지연의 원인은 아직 구분하지 않았습니다.

컴파일러의 현재 `bodyexecution.Execute`는 매 호출 임시 작업 폴더를 만들고
프로그램을 빌드합니다. 프로그램은 표준 입력에서 현재 정수 배열을 읽습니다.
그러므로 같은 바디를 반복 검사할 때 실행파일을 한 번 보관할 수 있는 구조입니다.
같은 부품을 계속 확인할 때 검사대 위에서 공작물을 매번 버리지 않는 방식입니다.

## 변경의 범위

Go 실행기 한 인스턴스가 최신 실행파일 한 개와 자신의 임시 폴더를 소유하도록 합니다.
원본 소스, 조립 계획과 생성 관측의 재검사는 매 요청 수행합니다. 현재 기대값과
입력을 실행파일에 보내고 두 번 실행하며, 결과나 합격 판정을 재사용하지 않습니다.

재사용 키에는 생성된 Go 바이트, 드라이버 계약 버전, Go 도구 바이트 지문,
Go 버전·OS·아키텍처와 현재 실행기 구현의 지문을 넣습니다. 실행 전 보관한 파일의
지문을 다시 읽습니다. 파일이나 계약이 바뀌면 새로 빌드합니다. 원본 지문과 부모
관측 연결은 매 요청의 새 보고서에 남기고, 빌드 기록은 실제 빌드·재사용 여부와
이전 빌드 지문을 구분합니다. 비어 있는 빌드 시간을 새 빌드처럼 집계하지 않습니다.

인스턴스 종료와 취소 시 자식 프로세스와 임시 파일을 정리합니다. 병렬 호출은
소유권과 취소 경로를 먼저 정한 뒤 실험합니다. 첫 구현은 한 실행기의 순차 호출로
범위를 좁히고 저장 공간 한도를 유지합니다.

## 먼저 작성할 검증과 비교

1. 같은 바디·같은 입력은 현재 실행 결과와 같으며 두 번째 빌드는 재사용됩니다.
2. 같은 바디의 다른 입력·기대값은 새 실행 결과를 냅니다. 이전 합격이 남지 않습니다.
3. 소스, 계획, 생성 결과, 실행파일 또는 Go 도구 바이트가 바뀐 경우 각각 검사합니다.
4. 위조한 부모 관측, 잘못된 연결과 미충족 기대값은 기존 실패를 유지합니다.
5. 빌드 중 취소, 실행 중 취소, 종료 뒤 재호출과 반복 종료를 검사합니다.
6. 네 계산 계열의 기존 한영 과제를 원본 실행기·보관 실행기로 번갈아 처리합니다.

관측 수는 완료 후 집계합니다. 추가 모델 학습 없이 같은 가중치로 생성하고,
생성된 Go·전체 실제 값·원본 실패를 비교합니다. 소스 재검사, 빌드, 첫 실행,
재실행, 전체 시간, CPU, 상주 메모리와 임시 저장 공간을 따로 기록합니다.
서로 다른 OS의 첫 실행 비용도 따로 읽고, 느려진 사례까지 공개합니다.
