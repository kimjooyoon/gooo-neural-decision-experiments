# Gooo 소스에서 짧은 조립 계획 만들기

2026-10-03. 최근 Meta의 조립식 절차에서 참고한 원리는 **이미 있는 자료에서
작은 작업 절차를 꺼내 쓰기**다. Gooo의 `computes`가 바디 구조를 제공하고,
짧은 JSON은 바꿀 수 있는 위치와 한영 의도만 지정하도록 연결했다.
소스에서 타입·변수·연산 구조를 계산하므로 이 부분에 추가 학습을 쓰지 않는다.

예를 들어 뺄셈 세 번을 가진 함수에서 ‘첫 번째 피연산자 순서’, ‘두 번째 순서’,
‘마지막 순서’만 선택 대상으로 지정한다. 자체 소형 모델은 이 세 선택을 한 번에
판단한다. 테스트 결과를 추가하면 남은 후보를 좁히고 바로 조립할 수도 있다.
부품 목록을 다시 쓰는 대신, 도면에 움직일 관절만 표시하는 방식이다.

컴파일러는 다섯 선택을 지원한다: 피연산자 순서, 분기 배치, 변수 참조, 대입 대상,
인접한 두 문장의 순서. 이번 실측은 그중 뺄셈 세 번인 한 과제에 한정했다.
[PR #1168](https://github.com/kimjooyoon/meta-ontology-go/pull/1168)에는 조건문·대입·참조의
별도 회귀 검사와 실제 CLI 실행 검사를 포함했다. 공개 시점에는 CI와 배포가 진행 중이다.

## 확인한 결과

- 계획 문서 크기: 같은 압축 JSON 기준 1,538 → 569바이트, 약 63% 감소.
- 24회 생성·48회 컴파일된 실행, 12개 비교 쌍의 확장 계획과 생성 코드가 같았다.
- 자체 모델의 실제 판단은 6회, 추가 학습은 0회였다.
- 기준 함수가 제공한 구별 입력을 사용하면 72/72 기대값을 충족했다.
- 최초 예시 하나만 사용한 조건은 독립 입력 12/72를 충족했다. 전체 조건은 84/144다.

모델 연결 시 전체 생성 중앙값은 전체 계획 8.14ms, 짧은 계획 8.60ms였다.
최대 RSS 중앙값은 17.33→17.64MiB, 프로세스 CPU는 한 코어 기준 86.78→86.53%다.
조건당 세 표본이며, 컴퓨터 전체 CPU 증가량은 측정하지 않았다. 짧은 계획을
펼치고 검사하는 비용이 추가된다. 이번 이점은 작성량 감소와 동일한 동작 연결이다.

예시 `10 -> -3`은 서로 다른 여러 조합이 만족한다. 실행 기준을 하나 더 얻으면
원하는 `7-input` 경로가 구별된다. Gooo에서는 이 차이를 모델 확신과 별도로
기록하고, 관측이 부족한 범위는 유한 충족률로 드러낸다.

최초 측정 도구가 ‘세 선택’을 ‘세 모델 호출’로 잘못 세어 멈춘 기록도 보존했다.
공동 판단 모델은 실제로 한 번 호출됐다. 계수 조건만 수정해 새로 수집했으며,
최초 기록은 위 집계에서 제외했다.

## 다음에 좁혀서 할 일

현재 선택 위치는 소스 순서의 번호이므로 소스를 고치면 함께 갱신해야 한다.
조건부 보정과 두 단계 갱신에 같은 방식을 적용하고, 작성량·구별 입력·전체 생성
비용을 각각 비교한다. 반복되는 원본 투영 비용을 재사용하려면 소스와 확장 계획의
일치 조건을 유지하는지 먼저 확인한다. 큰 모델이나 대규모 재학습 없이 진행할 수
있는 다음 언어 작업이다.
