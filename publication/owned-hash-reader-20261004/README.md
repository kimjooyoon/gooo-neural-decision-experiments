## 사용하면서 달라지는 것

실행기는 처음 파일을 확인할 때 32KiB 배열 하나를 만들고 같은 실행기의 다음
해시 읽기에 재사용합니다. 기존 직렬 실행 구간 안에서만 사용하며 종료·취소 때
참조를 해제합니다. 매 요청의 Go 공구 파일과 실행파일 전체 바이트를 다시 읽고,
각 실행 직전의 파일 확인과 두 실제 실행을 유지합니다. 크기 검사와 실제 읽기를
256MiB에 묶고 한 바이트를 더 읽어 초과를 알아냅니다. 읽은 길이가 초기 크기와
다르면 실패합니다. 이 확인의 범위는 열린 파일의 바이트·길이이며 원자적 파일시스템
스냅샷을 보장하지는 않습니다.

`--timing`의 터미널 안내는 도달하지 않은 단계를 `unobserved`로 표시합니다.
두 실행 중 하나만 관측돼도 전체 native 합계는 `unobserved`이고, 원래 JSON에는
도달한 개별 단계가 남습니다. 관측된 0은 `0.000ms`로 읽을 수 있습니다. 실패한
공구 조회가 예전처럼 실행 시간 `0ms`로 보이는 혼동을 줄였습니다. 기존 응답,
runtime v3와 파일 기록 형식을 유지합니다.

## 작은 버퍼를 선택한 근거

Go로 공구 실행파일과 이전 설치 Gooo 파일을 여섯 방식으로 각 16회씩 해시했습니다.
총 192회 해시이며 두 파일의 앞뒤 SHA256이 같습니다. 크기를 32/64/128/256/1024KiB로
바꿔도 공구 해시 시간은 일정하게 개선되지 않았습니다. Go 공구의 중앙값은 기본
14.22ms, 32KiB 14.95ms, 128KiB 14.26ms였습니다. 설치 Gooo 파일은 별도의 큰 파일
대용이며 생성된 작은 바디 실행파일과는 크기가 다릅니다. `hash-sizes-study.json`에
모든 원본과 자기 프로세스 CPU 시간이 있습니다.

구현 자체의 비교 벤치마크는 이전 기본 복사와 새 길이 제한·32KiB 보관 버퍼를
각 여덟 번, 매번 1MiB 파일 16회 해시합니다. 할당은 이전 약 **33.5kB/회**, 새
**0.8kB/회**입니다. 할당 횟수는 양쪽 9회입니다. 사용 중인 실행기는 버퍼 하나를
보관하고, 이 최초 준비는 재사용 벤치마크의 할당 밖입니다. 이 값은 해시 호출의
할당량입니다. 전체 컴파일러 RAM, 모델 RAM, 호스트 CPU 사용률은 따로 측정해야 합니다.

## 모델·결정론 실제 생성 비교

기존 한영 곱셈/덧셈 순서 원본 두 개, 모델·결정론 네 조건에서
**이전 → 후보 → 후보 → 이전**, 창마다 여섯 요청을 실행했습니다. 모두 `--timing`을
켰습니다. 이전 생성 Go와 요청당 128개 기대값을 고정했습니다. 자체 order judge의
16,384바이트 가중치 SHA256 `cf00ccc83d17d28ed73fcb869366151a48ffccd3aa8ca8e635aabf19810b9e78`을
그대로 사용했습니다. 조립은 설계도에 표시된 갈림길을 따라가는 일과 비슷합니다.
모델이 순서를 제안하고 컴파일러가 현재 원본과 실제 결과를 확인합니다.

| 관측 | 이전 설치 | 새 후보 |
| --- | ---: | ---: |
| 생성 요청 | 48 | 48 |
| 실제 모델 판단 | 24 | 24 |
| 실제 바디 실행 | 96 | 96 |
| 유한 기대값 | 6,144/6,144 | 6,144/6,144 |
| 최초 응답 중앙값, 각 8회 | 614.22ms | 628.93ms |
| 재사용 응답 중앙값, 각 40회 | 64.13ms | 65.88ms |
| 재사용 응답 범위 | 59.55–75.58ms | 57.38–79.16ms |
| 재사용 공구 전체 해시 중앙값 | 15.19ms | 15.03ms |
| 재사용 현재 자식 CPU 합 중앙값 | 12.82ms | 13.20ms |
| 재사용 최대 단일 현재 자식 RSS 중앙값 | 4,423,680B | 4,423,680B |

생성 Go 96개가 모두 고정 결과와 같았고, 저장 기록 읽기 전용 확인 16회도 통과했습니다.
공구/실행파일 재사용과 과거 빌드 기록, 매 요청의 원본 재검사·현재 자식 수·v3
분모를 확인했습니다. 첫 요청에는 공구 확인·빌드 자식이 각각 한 개, 재사용에는
두 바디 자식이 있습니다. 원래 실패와 첫 빌드·느린 관측도 보존합니다.

속도와 현재 자식 CPU 중앙값은 후보가 조금 높았고 범위가 겹쳤습니다. 한 장비의
기존 두 의도 반복으로 일반적 속도 변화는 판단하기 어렵습니다. 이번 성과는 보관
버퍼를 통한 할당 감소와 단계 표시 개선입니다. CPU/RSS 표는 현재 자식의 기록이며
부모 컴파일러의 해시 비용을 포함하지 않습니다. 추가 학습·새 의도 과제는 0개입니다.

## 원본과 재실행

[다음 작은 실험 계획](NEXT.md)은 순수 바디의 반복 실행 비용과 자체 작은 행렬의
세 값 저장을 다룹니다. 현재 관측에서 구간을 좁힌 후보이며 결과는 이후 실험에서 확인합니다.

설치본에서도 8회 생성·실제 모델 판단 4회·바디 실행 16회로 1,024/1,024와 고정 생성
Go를 확인했습니다. 모델 재사용 응답은 한영 69.42·62.53ms, 결정론 65.49·60.34ms입니다.
최초 응답 826.23·906.86·651.75·635.28ms도 원본에 보존합니다. 별도의 공구 조회
실패 한 요청은 모델 판단·바디 실행 0회, 128개 기대값 미관측으로 원래 종료 코드 1과
`native unobserved`를 보존했습니다. 저장 기록 확인은 성공·실패를 합쳐 5회 통과했습니다.
새 학습·의도 과제는 0개입니다.

실행 도구에 쓰기 상대가 없는 FIFO를 지정하면, 일반 파일 확인 전에 열기를 기다리는
문제도 발견했습니다. 검사 컨트롤러가 중단된 원본과 60초를 넘겨 살아 있던 해당
프로세스의 관측을 별도로 보존하고 종료했습니다. 일반 파일의 설치 실행 위 수치는
유지합니다. [후속 FIFO 수정과 실제 비교](../nonregular-tool-20261004)는 개발 #1198을
병합하고 main #1199의 자체 검사를 진행합니다. 후보의 실제 FIFO는 0.60초에 오류를
남기고 종료했으며, 새 같은 시간창의 일반 실행 비교에서도 유한 기대값을 유지했습니다.
