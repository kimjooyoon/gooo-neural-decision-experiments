완료했습니다. 병합·설치 상태는 후속 기록에서 구분합니다.

## 사용할 수 있는 기능

```sh
gooo body-path-run --source original.gooo --activity Name \
  --path-plan recipe.json --cases cases.json --out fresh-run --repeat 2 --timing
gooo body-path-run --verify-timing --out fresh-run
```

`--timing`을 켜면 원본 읽기, 경로 조립, 부모 기록 검사, 원본 재검사, Go 파일
해시, 공구 확인, 실행파일 준비·해시, 두 실제 실행, 결과 저장·결속의 시간을
남깁니다. `timing-summary.json`은 요청별 단계 시간을 밀리초로 모읍니다.
마지막 명령은 모델을 읽거나 새 프로그램을 실행하지 않고 저장 파일의 SHA256과
시간 기록의 일관성을 확인합니다. 파일을 바꾸거나 시간 구간이 겹치면 실패합니다.

기록기는 요청별 32칸 배열을 사용하고 별도 작업자를 만들지 않습니다. 기본 실행은
기록기를 만들지 않으며 기존 응답·요약·runtime v3 형식을 유지합니다. 실패한
요청도 도달한 단계와 원래 결과를 남깁니다. 실행하지 않은 단계는 생략합니다.

## 실제 모델과 결정론적 구성을 번갈아 관측

기존 한영 곱셈·덧셈 순서 파일 두 개에서 모델·결정론 네 조건을 사용했습니다.
각 조건은 **기본 → 기록 → 기록 → 기본**, 창마다 여섯 요청입니다. 최초 빌드
요청과 같은 실행파일을 재사용하는 다섯 요청을 구분했습니다. 원래 생성 Go와
128개 유한 기대값을 고정했고, 자체 order judge의 16,384바이트 가중치를 유지했습니다.

| 관측 | 기본 | 기록 옵션 |
| --- | ---: | ---: |
| 조립 요청 | 48 | 48 |
| 실제 모델 판단 | 24 | 24 |
| 프로그램 실행 | 96 | 96 |

생성 Go 96개는 모두 이전 설치 결과와 같습니다. 기록 옵션의 읽기 전용 확인을
여덟 번 따로 실행했습니다. 모두 통과했고 추가 모델 판단·실제 바디 실행은 0회입니다.
추가 학습·새 의도 과제는 0개입니다. 위 차이는 캐시·스케줄링 변동이 있는 한 장비의
관측이며, 기록 옵션의 속도 향상이나 순수 계측 오버헤드로 해석하지 않습니다.

## 어느 부분에 시간이 드는가

기록 옵션의 재사용 40회에서 얻은 단계별 중앙값입니다. 각 구간 중앙값의 합이
전체 응답 중앙값과 같을 필요는 없습니다. 단위는 현재 요청의 실제 경과 시간입니다.

| 구간 | 중앙값 |
| --- | ---: |
| Go 실행파일 전체 SHA256 | 14.46ms |
| 현재 원본·선택 재검사 | 3.10ms |
| 공구 내장 정보·보관 확인 결속 | 6.56ms |
| 보관 실행파일 확인·준비 | 3.44ms |
| 첫 실제 실행: 시작·대기·입출력 포함 | 9.34ms |
| 두 번째 실제 실행 | 8.75ms |
| 원래 결과 파일 저장 | 2.67ms |
| 저장 파일 SHA256 결속 | 0.72ms |
| 미배정 구간 | 0.11ms |

응답은 저장 전에 끝나고, capture는 원래 파일 저장·해시까지 포함합니다.
재사용 capture 중앙값은 68.02ms입니다. 초기 입력·모델 로딩, 계측 부속 파일·
요약 저장, stdout, 종료 정리는 capture 밖입니다. 생성 내부 시간은 바깥 generation
구간과 겹칩니다. CPU/RSS는 현재 자식만 집계했고 부모 컴파일러·모델 단독 RAM·
호스트 CPU 사용률은 측정하지 않았습니다. 과거 빌드·버전 프로세스는 현재 CPU 합에
넣지 않았습니다. macOS arm64, Go1.27.1 한 장비의 유한 반복 사례입니다.

공구 해시와 시작 비용이 조립 자체보다 큰 구간으로 드러났습니다. 다음 후보는
현재 파일 결속을 유지하면서 해시 읽기와 실행 준비 비용을 줄이는 방법입니다.
개선 결과는 동일한 원본·기대값과 실패 기록으로 확인해야 합니다.
